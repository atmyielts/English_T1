## Authority and data flow

1. The owning candidate, under the pinned monitoring policy and recorded consent, begins one open stream per camera, screen or microphone source. A restart creates a new recording/container rather than splicing a new initialization header into an old stream. New streams require an active, unexpired attempt. At most 64 recording restarts per monitoring session are accepted as a transport safety ceiling.
2. Each media segment reserves the next sequence, contiguous client-reported time interval, whole-content SHA-256 and exact ordered one-MiB part hashes/sizes. Segments are bounded to eight MiB and sixty seconds, one pending reservation per recording; a stream is bounded to 24 reported hours and 16 GiB. These are transport safety ceilings, not product entitlements, billing, device attestation or proof that a browser captured the claimed source/time.
3. The independent `workers/proctor-evidence` authenticates a user bearer plus a separate server-to-server evidence secret. Postgres rechecks candidate/session ownership on every authorization and receipt. R2 stores only application-encrypted parts under the reconstructed Proctor namespace. Conditional writes preserve the first envelope; retry/restart reads and authenticates that envelope before recording the canonical receipt. No public bucket, presigned bearer URL, cookie fallback or author-media permission grants evidence access.
4. Before committing a segment, the Worker reads all acknowledged parts, verifies canonical envelopes/AEAD/plaintext hashes and the whole segment hash, then commits in Postgres. A lost reply replays the same reservation/receipts without duplicate segment/audit creation. Until commit, reviewers cannot read the bytes.
5. Gaps are their own immutable, reasoned, contiguous sequence entries. Every reservation/gap advances a server-computed SHA-256 chain over the canonical `proctor.segment.v1` entry including the prior head. Closing requires the exact final sequence/head and no pending segments. `sealed` means the manifest cannot change; it does **not** mean uninterrupted coverage, identity verification or a valid academic outcome. Review must display gaps, pending segments, restarts and close reason explicitly.

Cryptography uses nonextractable HKDF-derived AES-256-GCM keys, random 96-bit IVs and a Proctor-specific key/AAD domain binding tenant, recording, sequence, part index, plaintext hash and length. It does not reuse Assessment asset keys or import another Worker's implementation. Each immutable receipt pins key ID, IV, ciphertext hash, object identity and storage ETag. Old key versions remain necessary for old recordings. Production KMS custody/rotation and legal deletion/holds remain required.

The canonical attempt → monitoring session → recording lock order matches pause/finalization. Reserved evidence can recover during pause and for one day after monitoring completion; completion does not silently discard saved footage. Reads stop at the recording's 90-day expiry even if encrypted objects still exist. This is an access cutoff, **not** implemented physical retention deletion. Legal holds, retention policy overrides, audited deletion and orphan cleanup remain launch gates.

## API and transport

The Proctor Edge namespace is `/functions/v1/proctor/recordings/`, with authenticated user JWT and `tenant_id` on each route. Exact frontend origins are enforced. Metadata bodies are bounded to 32 KiB and ten seconds; internal worker headers are not allowed by browser preflight.

| Route/action | Contract |
| --- | --- |
| `POST commands`, `recording.begin` | `recording_id`, `session_id`, policy-permitted `source`, supported matching `mime`; stable `Idempotency-Key` |
| `recording.reserve` | `recording_id`, next `sequence`, `start_ms`, `end_ms`, `previous_hash`, `byte_length`, `sha256`, ordered `{byte_length,sha256}` parts |
| `recording.gap` | Next sequence/contiguous interval/prior hash, explicit reason; no fabricated media |
| `recording.close` | Recording, `expected_sequence`, `expected_hash`, reason: `runtime_end`, `track_lost`, `user_stop` or `capture_error` |
| `GET <recording UUID>?after=0&limit=100` | Assigned, currently authorized reviewer only (including appropriately capable supervisors); audited manifest/segment page, numeric next cursor; no storage envelopes |
| `GET sessions/<session UUID>?after=<UUID>&limit=100` | Assigned-reviewer manifest discovery with keyset paging, gap/pending counts, close reason and retention cutoff; audited |
| `GET candidate/<recording UUID>?sequence=0` | Owning candidate's recovery checkpoint/selected segment binding only; current ownership/recovery cutoff, no reviewer playback or storage envelopes |
| `POST transport` | Worker-only dual credentials; `part.authorize`, `part.receipt`, `segment.complete`, `segment.read`; object/tenant identity reconstructed canonically |

Worker routes are `/v1/recordings/<UUID>/segments/<sequence>` with `tenant_id`: `PUT /parts/<index>`, `POST /complete`, and `GET` the verified committed segment. All use current bearer authorization, exact origin allowlists and `no-store`/`nosniff`/no-referrer headers. Reads require the review capability **and** current reviewer assignment/session access. Candidates and observers cannot use reviewer playback. The full segment is verified before returning any success/plaintext bytes. Bytes are returned as an octet-stream attachment for the authenticated review client; native public media URLs are not exposed.

## Capture and device recovery

`packages/proctor-web/src/capture.ts` acquires camera/microphone through explicit browser permission, or an entire display through a user gesture. Window/tab screen selection is rejected and its tracks are stopped. The application must first obtain current policy consent; this helper does not manufacture consent or provider proof. No permission or physical device is accessed automatically by importing the SDK.

`CaptureRecorder` uses real native MediaRecorder, bounded video/audio bitrate hints, five-second timeslices, ordered persistence and immediate physical track teardown on stop/track loss/storage or encoder failure. Browser support, focus/suspension and bitrate behavior still require device acceptance. A MediaRecorder stream is one container: later timeslices are **not independently playable files**. A review player must retain the initialization segment and concatenate/remux or use validated streaming support, while visibly preserving the recording timeline/gaps. Server decoder/transcoding/clip workflows are not implemented yet.

`CaptureJournal` persists binary footage encrypted in IndexedDB with actor/tenant/session scope, nonextractable AES-GCM keys, scope/recording/sequence AAD and Web Locks. Its second schema version preserves existing keys/segments and adds encrypted start/head/closure state. A 64-MiB pending-byte ceiling fails visibly and stops capture rather than silently deleting footage. Capture sequence checks prevent restarting an old container under the same stream identity. It survives reopening and isolates other scopes. The application still needs integrated Exam lifecycle, actor revalidation on candidate transport, trusted-device fencing, policy-controlled pause/end/restart/gap reconciliation and shared-device retention UX. The spool is not protection against malicious same-origin code/extensions or a compromised device.

`uploadCapture` hashes a saved segment into pinned parts and uses a deterministic reserve key. `CaptureUploads` now serializes each drain across documents, durably retries begin/close, compares saved bytes/intervals/prior head with a candidate-only canonical checkpoint and recovers a committed segment without a second reservation. It atomically saves the acknowledged head and removes that local segment only after matching canonical confirmation. A lost reply or interrupted device transaction retains footage; a foreign/different reservation or unknown advanced head fails explicitly rather than dropping it. Reloaded native capture must start a new recorder/container only after recovery/sealing, not reset the old sequence.

## Assigned-reviewer interface

The Proctor session screen now discovers authorized recording manifests and shows source/provenance, open/sealed state, gap/pending counts, close reason and retention cutoff. Timeline pages validate the exact server-serialized hash-chain entry and final manifest head without exposing envelopes. Missing footage, reserved uploads and empty recordings remain distinct from verified saved bytes. The interface retains Schood's mother-design primitives, native keyboard controls and responsive layouts without importing Academy/Platform application logic.

The private player streams supported MIME containers through native MediaSource, verifying each authenticated segment's SHA-256 before append. It buffers roughly 20 seconds ahead and trims older buffered content beyond a 30-second backward window; it does not download the entire recording into a Blob. There is no autoplay. A requested seek outside retained bytes rebuilds from the verified initialization and ordered container. This works locally for real native WebM/VP8 footage; it is not efficient indexed seeking for long recordings, universal browser/MP4 compatibility, server-sandbox validation or clip generation. Unsupported formats fail explicitly pending validated processed renditions. Transcripts/captions still require accessible workflow acceptance.

Each byte request freshly checks the captured signed-in actor. A five-second current-authority check also stops and releases already buffered footage if authorization cannot be confirmed. Account/session/unmount/clear paths abort pending byte reads, stop native playback, remove its source and revoke the object URL. A late initial manifest response cannot recreate playback after teardown. Reviewer bytes are memory-only; no JWT appears in a media URL or local recording cache.
