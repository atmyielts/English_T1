# Integrations: webhooks and API clients

Status 2026-10-22: **locally evidenced, incomplete; both off by default.** Backlog: `ENT-02` and `ENT-04`.

## Webhooks (ENT-04)

Events are deliberately thin: type, IDs and time only. Consumers read details through authorized APIs, so no answers, scores, keys, media or other-tenant data are ever sent.

| Event | When | `data` |
| --- | --- | --- |
| `registration.created` | registration inserted | `registration_id`, `window_id` |
| `attempt.submitted` | attempt submitted or expired | `attempt_id`, `registration_id`, `state` |
| `result.released` | grading release recorded; delivered no earlier than `release_at` | `release_id`, `attempt_id` |

Body: `{id, type, sequence, created_at, tenant_id, data}`.

Headers:
- `Schood-Event-Id`
- `Schood-Event-Type`
- `Schood-Delivery-Attempt`
- `Schood-Signature: t=<unix>,v1=<hex>[,v1=<hex>]`, an HMAC-SHA256 of `"<t>.<body>"`

During a 24-hour rotation overlap the signature header carries one `v1` for each secret. Consumers should reject timestamps more than 5 minutes old, and use `id` or `sequence` to de-duplicate and reorder. The reference verifier is `verifyWebhook` in `packages/assessment-core/src/webhooks.ts`.

**Endpoints**
- Public `https` with a domain name only: no IPs, local names, ports other than 443, credentials or fragments.
- At most 10 active per institution.
- Managed under `team.manage` with revisions and audit.
- The signing secret is generated by the Edge function and shown once. It is stored only as AES-GCM ciphertext (`ASSESSMENT_WEBHOOK_KEYS` / `ASSESSMENT_WEBHOOK_ACTIVE_KEY`, rotatable key IDs).
- Replaying a create key never returns a secret that differs from the stored one.

**Delivery**
- `workers/assessment-webhooks` runs on a cron with no public route. It claims signed deliveries from the Edge internal plane (shared `ASSESSMENT_WEBHOOK_DISPATCH_SECRET`), POSTs with redirects refused, re-validates the URL, times out after 10 seconds and caps concurrency.
- It reports only the status code.
- Leases are fenced by token, so a late report cannot overwrite a newer outcome.
- Retries back off exponentially from 1 minute, capped at 6 hours with jitter, then the delivery goes dead after 8 attempts. Staff can replay a dead delivery. Disabling an endpoint stops its pending deliveries.

**Flags:** `ASSESSMENT_WEBHOOKS_ENABLED=false`. With the flag off, the internal plane returns no work.

## API clients (ENT-02)

- Institution staff (`team.manage`) create service accounts with explicit scopes: `registrations:read`, `registrations:write`, `results:read`, `events:read`.
- The client secret (`sk_…`) is shown once; only its SHA-256 is stored. Rotation keeps the old secret valid for 24 hours. Revocation deletes every token immediately.
- A client acts with the **current** authority of the staff member who created it. If that person loses the capability or their membership, the client stops working.
- Writes are idempotent per client key and audited as `actor_kind = 'integration'`, attributed to that accountable staff member.

Flow:

```
POST /functions/v1/assessment-cloud/oauth/token    (client_credentials; Basic or form)
→ { access_token: "at_…", token_type: "Bearer", expires_in: 900, scope }

GET  /functions/v1/assessment-cloud/v1/registrations?window_id&after&limit
GET  /functions/v1/assessment-cloud/v1/results?window_id&after&limit     (released, due, latest generation, totals only)
GET  /functions/v1/assessment-cloud/v1/events?after=<sequence>&limit     (reconcile missed webhooks)
POST /functions/v1/assessment-cloud/v1/registrations  (Idempotency-Key; {window_id, candidate_id})
```

Every response carries `Schood-Api-Version: 2026-10-22`. Pages return `next_after`. **Flag:** `ASSESSMENT_API_CLIENTS_ENABLED=false`.

## Evidence (local)

- `supabase/tests/assessment-webhooks.integration.sql`:
  - authority, idempotency, and no secret in receipts or reads
  - producers fire exactly once with thin data
  - fan-out, claim and lease, retry backoff, stale-lease refusal and success
  - 8-attempt dead letter and replay
  - rotation overlap, a scheduled release held until its time, and disable
  - delivery history paging and grants
- `supabase/tests/assessment-api-clients.integration.sql`:
  - authority, and the secret kept out of command identity, replays and lists
  - token issue, wrong secret and missing scope
  - integration write attribution and replay
  - registration and event paging
  - results matched against an independent count
  - rotation and expiry, the creator losing authority, revocation and grants
- Handler, signing and delivery tests: `webhooks.test.ts`, `webhook-handler.test.ts`, `deliver.test.ts`, `api-handler.test.ts`. They run in the `integrations` CI job.
