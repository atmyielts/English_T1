# Academic audio, video and file answers

Status: the complete local center→candidate→scanner→blind double marking→independent approval/release→candidate-result journey passes using actual applications, production handlers/repositories, PostgreSQL, coordinator, encrypted R2 and real ClamAV/full decoding. Separate synthetic-service UI/device checks remain useful but are no longer the only answer-specific evidence. Identity/membership, PostgREST transport and internal job dispatch are explicit fixture adapters; native sources are generated, not personal devices. This is full-service implementation in progress, not hosted/release acceptance. `ASSESSMENT_MEDIA_ANSWERS=false` remains default-off; compatible-client/capture-format checks and all full-service launch gates remain mandatory. No production resource changed.

## Product and ownership boundaries

Academic answers belong to Assessment Cloud. They are not Proctor evidence. An answer cannot be a Proctor recording ID, public URL, caller-created storage receipt or caller-provided score. The Assessment media Worker, encrypted private R2 parts and separately authenticated scanner transport are reused; Proctor sessions, permissions and findings are not.

The twenty-second additive service migration introduces an immutable `assessment_answer_assets` binding and separate command receipts. Every new artifact has an immutable purpose (`prompt` or `answer`); historical prompt assets retain their original meaning. Answer assets are excluded from prompt libraries, prompt attachment guards and author cancellation commands, including when staff also sit an examination. A deferred constraint prevents an academic artifact from committing without its binding.

## Timing and authority

```text
candidate's completed local file
  -> exact ordered one-MiB SHA-256 manifest
  -> admit under current exam/section clock and device lease
  -> opaque immutable answer reference
       -> coordinator response.append before deadline: selects the answer
       -> encrypted part transport: may recover after academic finalization
            -> quarantine -> trusted scan/decoder -> marker access
```

Admission and answer selection are distinct commits. Reserving or uploading a file does not select it. The candidate explicitly chooses **Use this answer**, which obtains/replays admission under the coordinator's current lease and saves the opaque reference through the normal encrypted response journal before the academic deadline. The interface distinguishes encrypted device bytes, locally queued selection, server-confirmed selection, transport progress and scan state. A file picker, a completed take or an upload receipt never selects an answer by itself.

Candidates can also explicitly clear a selected answer while its question/lease/clock remain open. Confirmation is pinned to the reviewed selection, receives keyboard focus, and cancellation returns focus without writing an answer. Clearing journals JSON null through the normal ordered coordinator command; it does not remove the encrypted device copy, cancel the admitted upload or rewrite prior responses. The UI distinguishes a device-held clearing request from server-confirmed no-selection. A sealed copy can be reselected only before the deadline.

Connected verification exposed and corrected a cross-component device-proof mismatch: the established coordinator stores a SHA-256 digest of the canonical JSON token string, while answer admission initially hashed raw token bytes. Admission now uses the existing canonical hash contract; its regression test compares directly with the real coordinator digest implementation and still rejects caller-supplied hash authority. No stored lease, deadline, epoch or replay guard was changed.

New admission locks the owning attempt and validates the current device, token hash, lease epoch/expiry, active state, overall and section deadlines, current-section question membership, immutable question policy and exact part lengths/digests. Capture-policy enforcement runs before admission; its committed pause is a non-receipt rejection, not an acknowledged answer.

The canonical `content_hash` binds attempt, question version, source, MIME, total byte length and every ordered plaintext part digest. It is computed by PostgreSQL and is not an R2 completion hash. A completed storage manifest additionally binds encryption envelopes/receipts. This distinction allows a pre-deadline selection without waiting for transport or scanning, while preventing later content substitution.

The journal accepts only `{schema_version:"assessment.media-answer.v1",artifact_id,content_hash}` or explicit JSON null to clear. It checks exact tenant/attempt/question/hash binding and a non-cancelled/non-rejected artifact. No identity, filename, URL, storage envelope, score or scanner claim belongs in the academic answer.

Transport recovery remains limited to the authenticated owner, the pinned bytes and the immutable 24-hour upload expiry. It cannot select another answer, append journal entries, advance sequence, renew an exam lease or extend a clock. Exact admission receipts can be replayed after finalization. Already selected assets cannot be cancelled through either upload namespace; future deletion must use the separate retention workflow. Up to twenty immutable reservations per attempt/question are a transport safety ceiling, not product billing or an institution's configurable take policy.

The twenty-third migration adds a candidate-only opaque `admission_key` to the existing bounded catalogue. A matching stable device key recovers a committed admission whose reply or local binding checkpoint was lost. It does not confer a new lease, admission or selection. An index binds lookup to tenant/actor/immutable artifact receipt. No raw device token, storage key or encryption envelope is returned. The authenticated Exam home screen discovers only this actor/tenant's saved local attempt scopes and can reopen pending uploads without restarting an attempt, including after submission or when new admissions are disabled. Recovery-only transfer refuses to create an admission if no prior receipt matches.

## Contracts and routes

All browser routes are under `/assessment-cloud/answers`, require actual user authentication, tenant context and allowed origin, and return `Cache-Control: no-store`.

| Route | Purpose |
| --- | --- |
| `GET uploads?tenant_id=…&attempt_id=…&item_version_id=…` | Owning candidate's bounded upload/recovery catalogue; works when new admission is disabled |
| `POST commands`, `upload.begin` | Stable-key admission with attempt, question, source, exact upload manifest and current raw device credentials; Edge hashes the token and strips caller authority |
| `POST commands`, `upload.cancel` | Stable-key cancellation of an unselected, unfinished own asset; works while admission is disabled |
| Existing media Worker part/completion routes | Verified encrypted transport through the dual-authenticated artifact authority, with purpose-specific canonical authorization |
| Existing media Worker GET with `task_id` | Scan-ready bytes for the currently authorized assigned marker or moderator and the exact immutable task response |

An artifact read cannot combine `attempt_id` and `task_id`. UUID normalization, bounded metadata and stable idempotency keys apply. Database functions are service-role only; renamed prompt/grading helpers and all trigger functions are private, so their older authorization paths cannot bypass the new purpose boundary.

The public immutable question policy is `assessment.media-policy.v1`: allowed MIME formats, maximum bytes and allowed sources (`upload`, `capture`). Formats must match audio/video/file questions; file answers support PDF and single PNG/JPEG/WebP images, audio supports MP3/WAV/OGG plus native audio WebM/MP4, and video supports MP4/WebM. The twenty-fourth migration extends reviewed audio policies and the existing purpose-isolated prompt transport without rewriting historical question versions, answer bindings or receipts. MP4 audio recordings use a `.m4a` device filename, not a video label. The total artifact ceiling is two GiB. The `capture` source is a candidate-produced source label, **not trusted device attestation**. Per-question duration/take limits, richer documents and broader device/container validation remain required.

New native recordings are validated as their declared container and stream kind, not renamed to WAV/OGG. The scanner verifies actual WebM EBML DocType, permitted WebM codecs, MP4 brands, required audio/video streams, no embedded non-media streams, audio-only isolation and bounded dimensions. Streaming WebM/fragmented MP4 can lack a duration header: a successful complete decode must then provide positive bounded output timing; the six-hour safety ceiling still applies and any present invalid/over-limit duration is rejected. Every media file is fully decoded. This uses FFmpeg's documented [machine-readable progress output](https://www.ffmpeg.org/ffmpeg.html#Advanced-options) and [null muxer](https://www.ffmpeg.org/ffmpeg-formats.html#null), not an estimated duration supplied by the browser. This technical ceiling is not an institution's recording-duration policy.

Client start/preparation compatibility is separately versioned as `assessment.media-delivery.v2`. Historical `assessment.media-answer.v1` remains the immutable journal/binding format; it is no longer accepted as a client capability claim. Earlier clients could probe a native audio codec while lacking the corresponding store/contract format support. Both server and current client now reject that older delivery claim before starting the academic clock. Text-only exams retain their existing compatibility behavior.

## Marking and privacy

The actual institution interface now provides type-matched format checkboxes, standard size choices with an explicit exact-byte custom option, upload/recording source controls and read-only candidate previews. Rules survive immutable question revision and encrypted incomplete-draft restoration without rounding custom byte limits or manufacturing an answer key. Authors may create these drafts; this does not enable candidate delivery. Independent review displays the rules alongside the existing reviewed rubric.

The actual marking interface renders scan state, protected native image/audio/video and browser-streamed PDF downloads instead of raw reference JSON. Reads carry the assigned `task_id`, never candidate context or bearer URL parameters. Existing authenticated native-media loading and decoder teardown are reused. Download initiation revalidates the current account/task after asynchronous session lookup. The Worker supplies `Content-Disposition: attachment; filename="assessment-answer.pdf"` for assigned-task PDFs: the page's cross-origin `download` attribute alone did not control the browser's suggested filename. No original candidate filename enters that header; normal prompt documents also have a generic name, and native image/audio/video remain inline. Real browser downloads verify the generic filename. A stale/revoked assignment still fails canonical authorization even if an old view remains open.

Existing grading generations continue to create human-marking tasks for subjective questions, including while an attached file is still uploading/scanning. The immutable task stores the opaque answer reference; current scan state is a separate `answer_asset` projection. It exposes only artifact ID, kind, MIME, byte length and state. Candidate identity, original filename, owner, upload source and admission timestamps are not added to blind marker context or response snapshots.

Marker bytes require the current task assignment/capability and exact task/reference binding on every authorization. Revocation removes access. Institution bank permissions alone do not grant answer access. Candidate downloads require their exact own attempt context. Quarantined, rejected, cancelled or missing assets cannot be read; database mark/adjudication insertion guards prevent grading an unready referenced file even if a caller bypasses the interface. Scanning never awards a mark or invalidates an attempt.

Filename suppression does not anonymize spoken names, faces, embedded document metadata or identifying content in the answer itself. Institutional assessment policy, candidate instructions and any required redaction/processing remain necessary. A rejected or missing answer needs an audited institutional exception/remediation process; the current implementation deliberately does not turn it into an automatic zero.

### Local byte and native recording recovery

`AnswerFileStore` uses a separate `schood-academic-answer-files` IndexedDB database, candidate/institution/attempt-scoped nonextractable AES-GCM keys, encrypted state/filenames and fixed one-MiB chunks with an encrypted replaceable tail. Every tail change gets a new nonce. Tail/chunk bytes and their length checkpoint commit atomically under cross-document Web Locks. Matching-prefix replay supports lost local receipts/reselection; conflicting bytes, sealed edits, foreign scopes and changed canonical bindings are rejected. Sealing hashes every exact ordered chunk without assembling a multi-GiB Blob. Parts are reverified before upload. Explicit device-copy discard is not a server cancellation or deletion command.

`AcademicRecorder` accepts a separately supplied academic MediaStream; it does not request permission, reuse a Proctor recording, start an exam, admit/select an answer or upload bytes. Actual native recorder events drain into that store. It preserves all ordered data through normal stop, stops tracks synchronously on interruption/error, bounds queued unsaved data to 16 MiB and refuses to label a failed or interrupted prefix as a completed sealed answer. A completed take remains sealed if later teardown is repeated. Individual native chunks are not assumed playable; the completed sequence is the recording, consistent with [W3C MediaStream Recording data handling and stop ordering](https://www.w3.org/TR/mediastream-recording/#data-handling).

These keys persist in the same browser profile. Scope fencing prevents accidental UI crossover, not access by an OS user or hostile same-origin script. Browser storage can still be cleared. Only committed chunks/tails are durable; the newest undelivered recorder event can be lost on a browser/process crash. Interrupted prefixes require explicit recovery/decoder validation and cannot be called complete merely because some bytes survived. Local storage currently has a 64-file catalogue safety ceiling; product take policies, receipt-driven cleanup, retention/shared-device handling, larger offline workloads and cross-device recovery remain required.

The recorder now waits for the native encoder's `start` event instead of treating successful constructor/codec probing as recording readiness; bounded startup failure stops tracks and retains only an unsealed preparation. Startup-sensitive generated-source checks prompted this additional guard. The test source also explicitly requests frames so hidden/offscreen canvas behavior is not mistaken for a valid recorded take.
